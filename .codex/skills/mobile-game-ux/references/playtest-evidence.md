# Playtest evidence

Read when verifying a playable slice or reporting design quality. Original synthesis, 2026-10-12. Source anecdotes are hypotheses, not benchmarks.

Capture actual output at named device/window sizes: learning, representative busy play, failure/result and pause/menu. Compare the same scene/seed, camera, assets and settings before/after where possible. Record evidence paths in the target project. Inspect at real display size for hierarchy, text fit, cutouts, finger occlusion and consistency.

Exercise primary action, preview/commit/cancel where applicable, retry, back and pause/resume on the playable build. A screenshot cannot prove responsiveness, gesture ownership or enjoyment. State precisely which device/emulator, build and input were checked; emulated pointer input does not prove real thumb comfort or hardware performance.

When a new player is available, give a goal and observe before coaching. Separate usability (understood goal, predicted action, errors, recovery) from enjoyment/feel (choices, frustration, desire to retry). Record actual observations, sample limits and agreed timings. Do not invent retention targets or infer long-term engagement from a few testers. Without players, label expert review; without a run, label static review.

For each finding record problem, consequence, proposed change and verification. Recheck affected states after changes. Do not add more features when the selected slice needs clearer evidence.

Evaluate the guidance itself with the same realistic task, assets, engine and target before/after. Skill contracts and routing checks validate structure, not design effectiveness. A reproducible gameplay artifact and observed behavior are stronger evidence than agent count or document length.
